meta

One workspace for many git repos, built for people who live in the terminal and pair with AI agents.

Open with the one-liner: meta treats a folder of independent git repos as one workspace. Audience: developers who use git daily and run AI agents (Claude Code and similar) from the CLI. The nine squares are repos; the orange one is the workspace.

Ten repos. Ten copies of everything.

A cross-repo change means N clones, N branches and N pull requests, all by hand. An agent working across them gets lost.

Make this relatable: everyone has a folder of repos that drifted. Each card is a repo with its own flavour of drift. The cost is the manual loop for cross-repo work, and agents suffer most because they have no map of the fleet.

What it is

One manifest lists your repos.

{
  "projects": {
    "api": "git@github.com:acme/api.git",
    "web": "git@github.com:acme/web.git",
    "tooling": "git@github.com:acme/tools.git"
  },
  "scripts": { "test": "cargo test" }
}

A .meta file at the workspace root. The repos stay independent: own history, own remotes, own CI.

plugins: git, exec, run, worktree

The manifest is plain JSON (YAML and TOML also work via meta init --format). Projects map a name to a git URL or local. Scripts live in the same file. The CLI is a thin core plus plugins; the plugins do the work across the child repos.

Every multi-repo run ends with one results table: what worked, what was skipped, and why.

Pull, push, fetch, checkout and sync all fan out the same way. Repos with uncommitted changes or no upstream are skipped with a reason instead of failing the run. The table is real output format from the README.

Daily workflow

Run anything everywhere, or just here.

Any command, every repo, in parallel.

Named scripts

Scripts live in .meta, so the team shares them.

Directory-aware

cd plugins/
meta git status

Scope follows your cwd. Use -w for everything.

Scope rule: inside a project it acts on that project; inside a folder of projects it acts on those; at the root it acts on all. The -w flag forces the whole workspace from anywhere.

Daily workflow

One branch, every repo, no stashing.

$ meta project add my-app git@github.com:acme/my-app.git
$ meta worktree add feature/x --all

Projects are bare by default. Each branch is its own folder, and a worktree_init hook can run your install step on creation.

workspace/
└── my-app/
    ├── .git/       bare repo
    ├── main/       default branch
    └── feature-x/  new worktree

Bare-first layout is the default; set default_bare to false in .meta (or bare false per project) for traditional clones. Cross-repo worktrees are what make parallel work, human or agent, cheap.

AI on the CLI

Give every agent its own worktree.

One worktree per task means parallel agent sessions never trip over each other, and one meta command reaches all the repos a task touches.

agent A: feature/auth

agent B: fix/cache

agent C: chore/deps

This is the key slide for the AI-on-the-CLI audience. Each agent session gets an isolated checkout, so there is no stash juggling and no cross-contamination. The same worktree add command with --all creates the branch in every repo.

AI on the CLI

Four ways to make an agent fluent in meta.

Context packs

A skill or CLAUDE.md that says what meta is and when to use it. Install with meta init --with-skill.

Callable tools

An MCP server so any MCP-capable harness can run meta git and meta exec directly.

Workflows

Slash commands, subagents and hooks. For example, a worktree per open PR with tests in each.

Configuration

Permission allowlists, MCP registration and workspace discovery tie the rest together.

From docs/HARNESS_INTEGRATION.md. Note the distinction: a meta plugin extends the CLI; a harness integration teaches an external agent to use the CLI. A good setup uses all four types together.

Use cases

Where it earns its keep.

Microservice fleets

Pull, test and branch across services with one command, and see one status table.

App plus platform repos

Keep a frontend, backend and infra repo in step while each keeps its own release flow.

Org-wide sweeps

Shallow-clone a whole GitHub org with --depth 1, then audit or search every repo.

Agent cross-repo changes

Point an agent at the workspace root so it sees every repo and works in isolated worktrees.

The org-wide sweep example comes straight from the README: loop gh repo list into meta project add with --depth 1.

Extending meta

Add your own commands. Any language.

Manifest plugin

Any executable plus a manifest file that declares its commands. Shell, Python or Go, with no protocol to learn.

Protocol plugin

A subprocess speaking JSON over stdio, with structured access to workspace state. A Rust SDK hides the protocol.

Module

A repo that bundles a plugin with the Claude skills that drive it, discovered when you add it as a project.

meta plugin install | list | verify | update | remove

Version pinning and optional checksums are built in. The rules and mcp features ship as external plugins in this very workspace.

Three plugin kinds exist: built-in (compiled in), protocol (subprocess, JSON over stdio) and manifest (executable plus manifest). Templates exist for Node, Python, Go and shell. A module is the distribution unit that bundles a plugin and skills. Sources: docs/PLUGIN_DEVELOPMENT.md and docs/MODULES.md.

Pattern 1 of 4

Hub workspace.

A meta repo holds only the manifest. Each child repo keeps its own history, remotes and CI. The hub gives you one place to run fleet commands and one place for an agent to start.

Pattern 2 of 4

Nested workspaces.

A team workspace lives inside an org workspace. By default meta acts on the nearest one; add --root to drive the outermost, and -w to span all its projects.

Patterns 3 and 4

Share tooling through a tooling repo.

Add your scripts, skills and CI templates as just another project in .meta. This repo does exactly that with its .claude, .github and scripts folders.

Scripts

meta run lint

One named script, defined once, run in every repo.

Agent skills

meta skill install

Skills live in one repo and install where agents look.

Modules

meta module enable

A repo can ship a plugin and its skills as one unit.

Pattern 3 is the shared tooling repo; pattern 4 is the module, a repo that bundles a meta plugin plus Claude skills so a project can contribute commands, not just code. Be honest in Q&A: meta does not sync files into child repos for you; it gives you one place to define scripts and skills and one command to run them everywhere.

The product doc sets the rule: default help and README lead with the multi-repo CLI, and agent features are explicit and labeled. Nothing about agents is required to get value from the fleet commands.

Honest limits

When not to use it.

SituationBetter fit
One or two reposPlain git
Atomic cross-repo refactorsA monorepo
Build graphs, caching, affected-only testsNx, Turborepo or Bazel
Coordinated package versioningChangesets or release tooling
Teams that never open a terminalA hosted platform UI

meta runs git and your commands across repos. It does not understand your build graph or merge changes atomically.

Say this plainly; it builds trust. meta is a coordination layer over independent repos, not a build system and not a monorepo substitute.

Honest limits

Not well suited yet.

A mod ecosystem

No module scaffolder, no registry or publishing story, and no module-level version pin yet.

Today: a module is a git repo in your workspace, plugins pin versions, and templates cover Node, Python, Go and shell.

Partial fleets

One manifest describes the whole fleet. There are no tags or profiles for cloning only a subset.

Today: disable projects, shallow clones, or split into nested workspaces.

These are gaps, not promises. The mod gaps come from the Out of scope list in docs/MODULES.md: module version pinning, a module init scaffolder, a publishing registry, and a discovery sweep beyond project add. Disabling projects is documented in docs/DISABLING_PROJECTS.md.
